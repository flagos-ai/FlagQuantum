# API Change Proposal 065: A multi-node evidence scope

## Status

**Approved by the repository owner and implemented by the integration lane. Every
acceptance item below is checked against its measured result.**

The change moved under review while it was implemented, and the record says so.
Two of the proposal's own premises were corrected before the code was written, and
each correction is stated where it applies rather than silently absorbed:

- the narrower scope had to stay exactly as it was, because a release payload
  already sealed against it is not re-sealable (`### 3. The existing three
  scopes do not move`);
- the world size could not be narrowed to eight ranks to fit the existing
  vocabulary, because the frozen workload does not fit in eight
  (`## Why the narrower world was not the answer`).

The change is one new value in an existing closed vocabulary, plus the manifest
re-freeze and contract tests that hold the vocabulary to the release contract it
serves. It adds no Stable Core root export, no function signature, no plan
property, no result field, and no serialization schema version. `EvidenceScope` is
not exported from `flagquantum`, is absent from `docs/public_api_v1.json`, and is
absent from `contracts/public-api-v0.2-baseline.json`, so no public-API snapshot
is regenerated by this change.

## Problem

### The MPS release contract declares a world the evidence envelope refuses

`benchmarks/manifests/mps_release_v1.json` freezes the release topology at sixteen
ranks over two hosts of eight devices each, because that is the cluster that
exists and the only sharded MPS configuration ever measured:

```json
"topologies": {"devices_per_node": 8, "local_world_size": 8,
               "minimum_multi_node_count": 2, "release_world_sizes": [16]}
```

The runtime-evidence envelope describes a run by an `EvidenceScope`, and each
scope fixes the exact device counts it carries. Before this proposal the
vocabulary was:

| Member | Value | Device counts |
| --- | --- | --- |
| `ONE_GPU_LOCAL` | `one_gpu_local` | 1 |
| `TWO_GPU_SEMANTIC` | `two_gpu_semantic_regression` | 2 |
| `SCHEDULED_SCALE` | `scheduled_4_8_gpu_scale` | 4, 8 |

Eight is one full host of this cluster. A two-host run was therefore not
*unmeasured*, it was *unrepresentable*: `create_evidence_artifact` refuses a
provenance record whose device count is not in the selected scope's set, and the
verifier refuses one for the same reason. Measured before the change:

```python
envelope_carries_world(1)   # True
envelope_carries_world(2)   # True
envelope_carries_world(8)   # True
envelope_carries_world(16)  # False
```

So the MPS release contract could be evaluated and never satisfied. The gate
reported `release_world_size_not_carriable_by_evidence_envelope`, which was the
correct report and also a dead end: the campaign could run the sixteen-rank leg
perfectly and still be unable to seal the result as release evidence.

### The bound was doing double duty

`SCHEDULED_SCALE`'s four-or-eight set was not an arbitrary cut. Four and eight
are the counts a single scheduling decision can place on one host, and the scope
name says so. Widening that member to `{4, 8, 16}` would have made one member
describe two different failure domains — a run that fits inside one host's device
set and a run whose communication crosses a network boundary — under a name that
claims only the first. That is precisely the misreport the repository's
non-negotiable rule 1 and engineering decision principle 9 exist to prevent, and
it would have made `evidence_scope` unable to answer the question it is read for.

## Why the narrower world was not the answer

The first version of this decision was to re-freeze the release topology to eight
ranks, two hosts of four devices, so that the existing `SCHEDULED_SCALE` member
would carry it and no vocabulary change would be needed. It was requested on that
basis and it is arithmetically impossible for this workload. Measured:

```
capacity_workload.logical_mps_bytes = 1236780012864   # 1.24 TB
two hosts x 8 devices = 16 ranks -> 72.0 GiB per rank
two hosts x 4 devices =  8 ranks -> 144.0 GiB per rank
usable device memory, A800-SXM4-80GB  = 79.25 GiB
```

The recorded sixteen-rank completion agrees with the first line: every rank
reports about 72.4 GiB, which is 91 % of the usable 79.25 GiB, so sixteen is
already the minimum world this workload runs in and not a round number chosen for
convenience. Eight ranks would need 144.0 GiB per device.

Shrinking the workload to fit would not have been a re-freeze either. The frozen
workload body hard-codes the sixteen-rank boundary set:

```python
if world not in {1, TARGET_WORLD}:
    raise SystemExit("16-rank capacity gate supports only 1 or 16 ranks")
```

and its digest, `a1d856dc…aab88`, is recorded in
`capacity_workload.premise_provenance.current_workload_body_sha256` and digest-
bound through `workload_definition_sources`. Changing `n_sites` to make eight
ranks fit would change the digest, retire the capacity premise, and replace a
capacity claim with a smaller one — which would clear the blocker by shrinking the
claim rather than by sealing it. That is the trade the repository's evidence rules
forbid, so the vocabulary was widened instead.

## Decision

### 1. Add `MULTI_NODE_SCALE` to `EvidenceScope`

```python
class EvidenceScope(str, Enum):
    ONE_GPU_LOCAL = "one_gpu_local"
    TWO_GPU_SEMANTIC = "two_gpu_semantic_regression"
    SCHEDULED_SCALE = "scheduled_4_8_gpu_scale"
    MULTI_NODE_SCALE = "multi_node_16_gpu_scale"
```

The member carries exactly sixteen devices, and the class docstring states why it
is not a wider `SCHEDULED_SCALE`: one host of the measured cluster is eight
devices, a workload can require more devices than one host has, and a run that
spans two hosts is a different class with a different failure domain rather than a
wider run of the same class.

Sixteen and not "sixteen or more": the scope table is an exact-set contract, and a
member whose set were open-ended would stop being able to refuse anything. An
eight-device run is still `SCHEDULED_SCALE`; a sixteen-device run is
`MULTI_NODE_SCALE`; a fifteen- or seventeen-device run is refused by both, which
is the behaviour the conformance test asserts.

### 2. The refusal is the envelope's, not the caller's

`_scope_errors` gains one row and keeps its existing message shape:

```python
EvidenceScope.MULTI_NODE_SCALE: {16},
...
raise ValueError(f"{scope.value} requires device count in {sorted(expected)}, "
                 f"got {device_count}")
```

Nothing else in the envelope changes. The completeness rule, the measured-field
rule, the 40-hex commit rule, the twelve-field `RuntimeProvenance` record, and the
`hmac-sha256` integrity envelope are all untouched, so this proposal does not
change what a `MEASURED_PRODUCTION_RUN` has to contain — only which device counts
it may contain it for.

### 3. The existing three scopes do not move

`ONE_GPU_LOCAL` stays `{1}`, `TWO_GPU_SEMANTIC` stays `{2}`, and
`SCHEDULED_SCALE` stays `{4, 8}`. This is not conservatism: the five signed
statevector envelopes in `benchmarks/results/scalability/` were sealed against
those sets, and a sealed envelope is an attestation over its own
`evidence_scope`. Changing a set that a promoted artifact was sealed under would
make the promoted artifact unverifiable without re-sealing it, which is a
different and much larger change than adding a member. The new member is
therefore additive by construction, and a test asserts that four-or-eight is still
exactly four-or-eight.

### 4. The gate derives carriability from the envelope, and the manifest discloses it

`benchmarks/internal/evidence/mps_release_gate.py::envelope_carries_world` decides
whether a world can be sealed **by asking `create_evidence_artifact` for each
member** rather than by copying the scope table. That is why this change needs no
gate edit: `envelope_carries_world(16)` became `True` when the member landed, and
would have become `True` even if the manifest had not been re-frozen.

`benchmarks/manifests/mps_release_v1.json` is nevertheless re-frozen, because a
manifest is a frozen document rather than a derived one:

- `release_payload_envelope.device_counts_by_scope` gains
  `"multi_node_16_gpu_scale": [16]`;
- `release_payload_envelope.carriable` flips to `true`;
- the note records that no MPS `measured_production_run` artifact exists yet, so
  `carriable` describes the envelope and not a run;
- `topologies.note` records the measured 8-versus-16 arithmetic above, so the next
  reader does not repeat the eight-rank proposal.

`carriable: true` is a statement about the envelope. It does not raise any claim,
does not satisfy any other gate requirement, and does not by itself move the MPS
capability on the maturity ladder. The MPS gate still reports the premise and the
speed ladder, and `scalability_claim_allowed` stays false everywhere it was false.

## Non-goals

- Any device count other than sixteen. A thirty-two-device scope, an eight-host
  scope, or a parametric scope are all separate decisions with separate evidence,
  and none of them exists on this cluster: there is no third host, so no run can
  be taken that would justify one.
- Any relaxation of what a `MEASURED_PRODUCTION_RUN` must contain. This proposal
  widens which device counts a payload may describe, not what a payload must say.
- Any change to `ArtifactClass`, `RuntimeProvenance`, the integrity scheme, or the
  `flagquantum_runtime_evidence_v1` schema. The envelope's root keys and its
  `integrity` keys are unchanged.
- Any change to the five promoted statevector envelopes in
  `benchmarks/results/scalability/`. They stay sealed against the scopes they were
  sealed against.
- Any claim. This proposal removes one named structural blocker from the MPS
  contract. It does not certify a run, does not raise
  `scalability_claim_allowed`, and does not promote a payload.

## Why this is an integration change rather than a lane change

`flagquantum/runtime/observability/evidence.py` and `tools/**` are protected
integration surfaces, and `benchmarks/**` is a shared path. The file that owns the
scope vocabulary is the file every capability's release evidence flows through, so
a member added for one capability's convenience is a change to a shared contract.
It lands here, with its own tests and its own record, rather than as an edit inside
the MPS lane.
