# API Change Proposal 004: Result, Measurement, and Noise Semantics

## Status

**Contract frozen — core semantics and machine-readable contracts received separate freeze approval.**

- Target version: first public alpha.
- Affected interfaces: `fq.plan`, `fq.run`, `Circuit.plan`, `Circuit.run`,
  `ExecutionResult`, `MeasurementResult`, and the `ExecutionPlan` noise extension.
- Root-level name changes: none.
- Authorization: the API owner explicitly authorized Proposal 004 implementation
  on 2026-09-01.
- That implementation authorization did not itself freeze the entire FlagQuantum
  API or the Result schema.
- Freeze record: on 2026-09-01, the API owner explicitly approved the exact
  Proposal 004 contract bound to the review packet. This does not constitute
  the overall first public alpha freeze.

## Problem

Proposal 003 established a serializable, verifiable `ExecutionPlan` that executes
exactly as planned. It temporarily retained separate measurement and noise paths,
while the result contract still exposed incidental backend behavior:

1. Explicit `measurements=` silently replaced measurements already in the IR.
2. `noise_model=` went directly to Runtime and could not be inspected, saved, or
   restored through `fq.plan`.
3. Programs with measurements or noise did not share the `fq.run(plan)` path.
4. `ExecutionResult.__getattr__` presented backend-native attributes as stable API.
5. Users had to inspect multiple optional fields without fail-closed accessors.
6. Result summaries lacked a schema and version for automated consumers.

## Decisions

### 1. All stable execution starts with a plan

`fq.run(program, ...)` must be equivalent to:

```python
plan = fq.plan(
    program,
    options=options,
    measurements=measurements,
    noise_model=noise_model,
)
result = fq.run(plan)
```

The stable path no longer retains transient measurement or noise execution.
`fq.run(plan)` continues to reject all options, measurement, and noise overrides
so that execution cannot diverge from the plan identity.

### 2. Measurements have one canonical source

- Final measurement requests must be stored in the plan's `CircuitIR.measurements`.
- `measurements=` is a convenience input for planning, not an execution override.
- Passing `measurements=` when the program already contains measurements must fail.
- Neither implicit replacement nor implicit appending is supported.
- Request order contributes to the program fingerprint and determines the order
  of `result.measurements`.
- The sample request generated by `ExecutionOptions(target="samples", shots=...)`
  is also stored in the IR.

Serialization, identity, restored execution, and auditing therefore use the same
measurement source of truth.

### 3. Noise is a verifiable plan extension

Stable entry points accept only `flagquantum.noise.NoiseModel`. The model is
stored as a strict extension in `ExecutionPlan.extensions`:

```json
{
  "namespace": "flagquantum.noise",
  "kind": "noise_model",
  "version": "1.0",
  "identity": "<sha256>",
  "payload": {"schema": "flagquantum.noise_model.v1"}
}
```

Reading a plan must reconstruct the NoiseModel and verify its identity. Unknown
fields, unknown extensions, multiple extensions, or an identity mismatch fail
with `extension_incompatible`. The first public alpha's stable noisy path
supports only `mode="auto"` and `mode="density_matrix"`. Other combinations fail
during planning, before any kernel executes.

### 4. Results use explicit accessors

Stable accessors are:

- `result.statevector()`: return the statevector or fail explicitly.
- `result.require_samples()`: return samples or fail explicitly.
- `result.measurement(index_or_name)`: select by position, metadata name, or unique kind.
- `result.expectation(...)`: accept only an expectation measurement.
- `result.native()`: explicitly retrieve the unstable backend-native object.
- `result.summary()`: return a summary with a schema and version.

Remove implicit native-attribute forwarding through `ExecutionResult.__getattr__`.
Stable accessors may use a backend-native object internally for conversion, but
its type, methods, and lifecycle are outside the compatibility commitment.

The candidate type of `MeasurementResult.value` is narrowed to:

```text
torch.Tensor | list[dict[str | int, int]]
```

These cover expectation/probability/sample values and counts, respectively. This
proposal does not promise cross-version JSON serialization of complete tensor
payloads. The stable contracts cover plans, result access semantics, and versioned
summaries, without implicitly serializing device tensors or autograd graphs.

## Compatibility Boundaries

- Retain `result.to_statevector()` temporarily as a compatibility spelling for
  `statevector()`.
- Retain `value/state/samples/measurements` fields temporarily for training and
  tensor composition.
- `metrics/provenance/runtime/compatibility` remain diagnostic mappings; this
  proposal does not freeze all of their keys.
- `Module.execute()` reuses `ExecutionResult`; Proposal 005 resolves the Module
  plan type.
- Retain the `noise_model` parameter name in this round so that naming and
  execution-semantics migrations remain separate changes.
- Dynamic circuits, provider job results, and deployment results are out of scope.

## Executable Acceptance Criteria

- [x] Explicit measurements enter the plan and execute after a JSON round trip.
- [x] Conflicting IR and explicit measurements fail without implicit replacement.
- [x] The plan stores the noise model payload and identity.
- [x] Noisy plans execute exactly after a JSON round trip.
- [x] Noise identity tampering fails before execution.
- [x] Program and plan inputs share the exact-execution path.
- [x] Result accessors fail explicitly for missing or ambiguous data.
- [x] Backend-native attributes no longer leak implicitly.
- [x] Summaries include a schema and version.
- [x] The API owner separately approved the contract freeze.

## Subsequent Decisions

Proposal 005 resolved the relationship between `Module`, `TrainingResult`, and
execution results:

1. `ExecutionResult.require_value()` is the fail-closed Module/training accessor.
2. Diagnostics use a schema/version envelope; section keys allow compatible additions.
3. `Module.forward` returns a Tensor; `Module.execute` returns an ExecutionResult.
4. `fq.train` remains a minimal optimizer loop; Module owns checkpoints.

The `noise_model` name, the `to_statevector()` compatibility window, and a unified
exception base remain for subsequent proposals. Proposal 005 does not expand its
scope to include them.
