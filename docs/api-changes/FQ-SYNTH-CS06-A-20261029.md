# CS06-A execution consistency boundary

Status: private integration proposal for review. The user authorized CS06-A
contracts, real seam tests and a PR. This does not approve or change stable
exports, ExecutionOptions, ExecutionResult, ExecutionPlan serialization, or
`fq.compile`. Classification: `single_device_fast_path`.

## Responsibilities

Compiler continues to own arithmetic candidates, gate conversion, optimization,
routing, layouts and resource estimation. Runtime owns the authoritative sealed
ExecutionPlan and execution. A private Services check composes those existing
contracts. Compiler adds only a pure CircuitLimits record; Runtime gains no
implementation or dependency. Services imports that single constraint authority.
The normal CS-04 facade/reader is unchanged and frozen for this stage. CS06-C
will replace its hash-only admission with this checked-plan seam, rather than
maintain two evolving validators. CS06-B owns selection; CS06-C owns
the final normal-user integration.

An execution plan already incorporates Runtime's compiler normalization. Its
serialized canonical program must agree with its actual instruction layers.
Check the requested basis, topology and limits against this executable, never
only against the submitted pre-planning CircuitIR. The existing `fq.run(plan)`
path executes that checked plan without replanning. Ordinary `fq.run(source)`
is admissible only when its resulting plan matches the checked plan/configuration.

## Limits and evidence

Hard final-resource limits are maximum allocated qubits, instruction count and
depth, including preparation and cleanup. These are distinct from ranking
preferences and construction/search budgets; CS06-A performs neither search nor
ranking. A maximum workspace constraint must be sourced from CS-05 allocation
history in CS06-B: CoreIR alone does not prove workspace ownership or cleanup.
CS06-A therefore does not accept an unchecked workspace count or expose an
unenforced workspace limit.

Reuse ResourceEstimate and the existing plan identity, program, options,
environment and compiler fingerprints. The only new private records are final
Compiler-owned CircuitLimits and a Services checked-plan view, because the existing plan records no
user resource ceilings or named logical-port binding. Returned resource records
are freshly derived; mutating a returned count dictionary cannot alter evidence.

Verification binds the sealed payload, actual canonical instruction layers and
raw Runtime execution controls. RuntimeConfig is validated through its existing
manifest parser and checked against the sealed backend/device/precision. Routing
diagnostics omitted by the existing plan deserializer are recovered as a view of
the canonical program witness; the plan itself is never patched. Altered instructions, precision/configuration,
noise, topology or routing controls are not accepted through an unchanged
payload identity. Verification and resource inspection never plan, compile or
execute. They do not authenticate manually forged result tensors or prove source
authorship; canonical-equivalent plans are compared as executable plans, not as
original Python transcripts. B must bind source/candidate/target identities to
this boundary rather than invent a source hash inside Runtime.

## Initially admitted profile

One exact local CPU torch/pytorch statevector, single batch, registered static
unitaries and no observations/measurements/noise. Basis names are validated by
the existing basis converter; valid-but-inexpressible bases remain conversion
failures, distinct from unknown names. This checker performs no conversion.

No routing uses an identity logical layout. Routed admission initially requires
the existing v1 undirected persistent-layout route, identity initial placement,
no allocated idle slots, an explicit matching CouplingMap and intact routed SWAP
evidence. Reuse Compiler's SWAP witness parser and Layout operations to replay
and check pre-restore/final permutations. Two-qubit locality is checked against
the requested topology. Logical named ports must be bounded and disjoint and
are projected through the verified layout, including a nonidentity final layout.

Missing/unknown/inconsistent routing, renamed final layouts, directed/allocated
routes and gate rewrites that destroy routed SWAP witnesses fail closed. This is
not a general imported-block proof system. B must provide a checked transformation
chain before expanding admission to post-routing conversions; deleting a routing
refusal or trusting `mapping_restored` is insufficient.

## Conformance

Use one consumer against live Runtime plans and a test-only recorded-plan replay
fake built through the existing serializer. Fake conformance is not numerical
evidence. Real CPU scenarios cover preparation/arithmetic, actual SWAP routing,
nonidentity output binding, phase preservation and pre/post execution agreement.

Negative scenarios include basis drift introduced during planning, final limits
that the source falsely appears to satisfy, same-width different programs,
changed options/controls, corrupted layers or layouts, missing route witnesses
and unsupported target combinations. The source-only Clifford+T preparation
probe must be rejected when the actual executable contains `u3`.

No user trial, public API release, CS06-B/C or Qmod compatibility is claimed by
this contract. Contract and conformance must land before those implementations.

## Handoff to B/C

| Fact | Authority and obligation |
| --- | --- |
| Source definition, preparation and logical ports | B must bind the existing definition/CoreIR content identity to the candidate and declared ports; this plan-only checker does not authenticate Python source transcripts |
| Workspace ceiling | B compares CS-05 allocation history, never a caller-authored count inferred from CoreIR |
| Final width/operations/depth | One pure Compiler CircuitLimits record over ResourceEstimate; no search-budget or objective overload |
| Basis/topology/transformations | Existing basis conversion records and Layout/CouplingMap; unsupported lost SWAP witnesses require a later checked chain |
| Executable/configuration | Existing sealed ExecutionPlan plus its actual layers and RuntimeConfig |
| Result association | Services checks that same plan, configuration, program, dtype and shape; tensor contents are not authenticated |

A test-only recorded-plan replay fake substitutes for the live plan producer
without changing the consumer. It uses the existing plan serializer, not a new
wire schema. The real Runtime probes supply the numerical evidence separately.
