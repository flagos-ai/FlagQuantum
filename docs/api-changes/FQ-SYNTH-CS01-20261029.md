## User problem and current executable workflow

Users should describe supported computation and quantum input semantics without
designing arithmetic gates, workspace or inverse sequences. Internally, that
requires information which gate-level IR no longer carries. This milestone
establishes the representation and boundaries before implementing gate lowering.

The existing workflow supported by this work is executable today:

```python
import flagquantum as fq

circuit = fq.Circuit(2).x(0).cx(0, 1)
options = fq.ExecutionOptions(
    mode="statevector", backend="torch", device="cpu", precision="complex128",
    require_gradients=False, allow_approximate=False, allow_backend_fallback=False,
)
plan = fq.plan(circuit, options=options)
result = fq.run(plan)
assert result.plan.identity == plan.identity
assert int(result.statevector().reshape(-1).abs().argmax()) == 3
```

No example in this milestone claims a high-level function has been synthesized.
Python capture, arithmetic gate generation, candidate selection, decorators and
Qmod execution remain subsequent deliveries.

## Coherent integer contract

For disjoint quantum inputs x, y, output z and zero workspace w, lowering must
eventually implement:

```text
U_f |x,y,z,0_w> = |x,y,z XOR encode(f(x,y)),0_w>
```

The formula applies linearly, including external entanglement, for every output
bitstring z. XOR is bitwise, not modular integer addition. A fresh zero target
produces the ordinary function result. Unsigned exact arithmetic requires enough
output bits; it does not truncate, measure, reset or add input-dependent phases.
Inputs preserve computational-basis values, not necessarily their reduced state
after becoming entangled with the result. The complete emitted inverse must be
the adjoint of the same chosen implementation.

Logical value uses such as x*x read one resource twice; they do not create copies
of an unknown state. Physical entry ports are injective and pairwise disjoint,
including views, output and workspace. Different port names cannot hide overlap.
This conservative first profile does not support consumed/mutable inputs,
in-place arithmetic, arbitrary local state, free, drop or bind.

Fresh-zero workspace is an allocator obligation. External zero workspace is a
caller precondition, explicitly distinguished from a proof. Unknown workspace
cannot be accepted for this contract, and compilation cannot inspect its state.
The XOR output itself need not be zero. Cleanup is a lowering obligation, not
something the CS-01 structural verifier has already proved.

Classical constants use the existing INDEX type with checked nonnegative Python
integers. Quantum values use `IRType("quantum.uint", (width,))`. Widths, constants
and limits reject bool or lossy numeric coercions. A trainable Tensor cannot
silently become a fixed integer. Discrete integers, widths and implementation
selection are not differentiable in this profile. Existing outer Circuit angle
bindings remain a separate concern; gradient compatibility is checked in CS-03/06.

## Representation decision

Reuse `_hybrid.model` directly: IRType, ValueId, Value, SourceLocation, Operation,
Block, Region and HybridProgram. A sequence of existing HybridProgram functions
and an entry name expresses an acyclic call graph. There is no third generic
program container, pass registry, serializer or public schema.

The closed construction verifier accepts these operations:

| Operation | Meaning |
| --- | --- |
| arith.constant | Nonnegative compile-time INDEX value; not a quantum register |
| qint.add / qint.multiply | Exact logical integer expression with a quantum operand |
| qint.call | Direct call with checked argument and result types |
| qint.return | Single final quantum-integer result expression |

Results are logical expressions, not physical allocations. The small verifier
checks conservative nonnegative upper bounds through calls to reject insufficient
widths; CS-02 owns full inference and lowering. It bounds definition/expanded
nodes, call depth and width, rejects recursive or unknown calls, regions,
unsupported effects and use-before-definition, and reuses existing Diagnostic
and HybridVerificationError. Source positions remain diagnostic-only and do not
change existing structured semantic identities.

The original hybrid verifier continues to reject these quantum integer ops;
classical arith.add is not reinterpreted. Existing hybrid transformations and
TraceGate are not assumed compatible: the latter cannot preserve every full
Core parameter/matrix payload. Opaque unitary blocks stay in existing CircuitIR.
The integration probe uses serialized tensor matrix data to preserve a global
phase under control and a three-angle U3. It does not declare every custom
matrix representation controllable or every serialized tensor differentiable.

## Dependency decision and CS-02 handoff

Allowed implementation direction:

```text
public/adapter boundary -> Compiler construction -> Core instructions/IR
Algorithms arithmetic wrapper -> Compiler pure arithmetic kernel -> Core
```

Compiler must not import Algorithms, Circuit, Runtime or Simulation. Merely
moving a function into an Algorithms submodule would not isolate that package's
eager imports. The existing Algorithms-to-Compiler direction already serves
resource estimation; this change also tests that the current algorithm consumer
and private compiler profile can be imported together. Architecture and dependency
checks remain authoritative.

CS-02 will extract the existing adder gate generator into a narrow private
Compiler kernel and migrate the existing Algorithms wrapper in a separate
domain-owned change. Inputs are widths/maps; output is existing Core instructions.
Keep adder_circuit/adder_qubits, their wire ordering and their carry/carry_out
semantics unchanged. Do not add a duplicate adder or a general provider registry.
The kernel is not extracted in CS-01: import-direction validation is evidence
for that decision, not a claim that replacement has already been demonstrated.

## Artifact and execution identity boundary

Logical construction and target-compiled checking are internal stages. The
future ordinary user receives one synthesis product and uses existing fq.run.
Target checking binds the exact final circuit/configuration/scope; composing,
recompiling or changing preparation invalidates that evidence for the new circuit.
No second public compile operation is required by this milestone.

The real CPU probe establishes:

| Information | Existing source | CS-01 conclusion |
| --- | --- | --- |
| Input circuit | CircuitIR/content_hash at the calling boundary | Retain before planning; raw source hash is not an executable identity |
| Executable identity | ExecutionPlan.program_fingerprint and plan_program | Available; canonicalization may remove gates or reorder independent layers |
| Executed instructions | plan_execution_program and plan.layers | Recoverable for the verified local static path |
| Result association | ExecutionResult.plan.identity | Available for explicit fq.run(plan); wrong same-width circuit has a different identity |
| Parameter values | Executable program fingerprint | Changed concrete angles change plan/program identities |
| Final layout | Existing Compiler final_layout and routing metadata | Verified on restore-after-each-gate routing with an actual inserted SWAP |

The normalized plan does not separately retain every raw input circuit or a
source-to-normalized transformation proof. A future integration boundary can
retain the source identity and validated execution plan together in the synthesis
product, then compare result.plan to that plan. This is a proposed bridge, not a
new Runtime field or a completed generic named-result reader. It must also avoid
silently changing execution options bound to a plan. Compiler does not import
Runtime to manufacture this association.

CS-06 must validate direct fq.run(program.circuit) association and any further
backend transformations before enabling automatic named decoding there. Until
then, fail closed for missing plans, unknown layout, untracked execution
transformations or stale parameter bindings. Do not compare only wire counts,
alter stable fingerprints, or rely on a hidden global object-address registry.

## Source-language compatibility implications

Qmod's highest numeric index is the MSB. FlagQuantum arithmetic register maps
and basis-label wire order are MSB first. A two-bit source numeric value 1 uses
source bit 0 but the last destination wire in an MSB-first map. CS-07 must test
non-palindromic values, indexed gates/slices and named readout; no source parser
or index conversion is claimed here.

Qmod Input consumes a reference; Const permits phase effects; free is an unchecked
zero assertion; drop retains non-reusable potentially dirty wires. None is mapped
to a classical constant or automatic clean workspace release in this profile.
Fresh assignment and the full-width XOR primitive share only the zero-target
case; truncated source XOR and wraparound addition require explicit later rules.

## Diagnostics, defaults and scope

Current structural failures use existing code/message diagnostics, with source
location embedded when available. Later resource diagnostics must distinguish:
requested/effective limits and their source, checked candidate facts, proved
bounds versus observed minima, and suggestions with their conditions. They may
not call a candidate failure globally impossible or change user semantics.

The delivery plan proposes width-first deterministic ranking and bounded search.
CS-01 defines this as policy, not an implemented optimizer: hard constraints
first; compare candidates only in the same basis/target; stable implementation
identifier breaks ties. CS-05/06 must supply measured tradeoff evidence before
promoting defaults. No resource-selection or gradient-support claim follows from
these representation tests.
