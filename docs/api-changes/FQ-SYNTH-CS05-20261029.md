# CS-05 private arithmetic scheduling boundary

Status: private Compiler implementation proposal under revision-six CS-05.
The user authorized lifecycle analysis, retained and cleanup/recompute schedules,
acceptance tests and a PR. No public API, stable schema or export is changed.

The existing construction verifier remains authoritative for immutable basis
borrows, full-width unsigned arithmetic, acyclic calls and disjoint physical
ports. Lifecycle analysis inlines calls into the existing HybridProgram records,
preserving repeated reads and source locations. It records direct uses and the
dependencies that must be available for exact inverse computation. A last use
does not certify that a value is clean or disposable.

One arithmetic emitter serves both schedules. `retain` preserves the current
default gate sequence and keeps results until the final reverse sweep.
`recompute` may uncompute operands between uses and rematerialize dependencies
before either forward computation or inverse cleanup. Only allocations returned
to zero by an exact inverse can reenter the zero-workspace pool. Both schedules
use the same existing ripple addition and multiply-accumulate kernels; no general
unitary inversion or assumed phase neutrality is inferred from opcode names.

Private `schedule_arithmetic` returns the existing CircuitIR with lifecycle and
allocation/event diagnostics. `lower_arithmetic` still returns CircuitIR and
defaults to `retain`; its optional private scheduling keyword does not change
stable Compiler exports. Candidate costs use the existing resource estimator.
The supplied workspace zero-state obligation and XOR output contract are the
same as before, including nonzero output targets.

Generated CircuitIR blocks compose through existing Circuit APIs and explicit
verified port bindings. Arbitrary external unitary blocks, mutation, free/drop,
escaping values and caller-authored cleanup assertions are not admitted as pure
arithmetic. A future general block boundary needs independent effect and cleanup
semantics; this change does not introduce a bypass.

Acceptance requires a fixed source workload with a strictly smaller real
workspace allocation under recomputation and strictly more operations, exact
permutations, complex amplitudes, controlled relative phase, clean workspace,
function-boundary alias preservation and fail-closed budgets. This is a bounded
deterministic scheduling heuristic, not optimal reversible pebbling or CS-06
constraint-based selection. Classification: `single_device_fast_path`.
